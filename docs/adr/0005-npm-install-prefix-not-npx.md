# Launch via `npm install --prefix`, not `npx`, against the tarball URL

A real user reported a newly-shipped settings section missing even after restarting `run.bat` several times, despite the code being verified correct and pushed to `master`. Root cause, confirmed with a controlled local test (a tiny HTTP server serving a tarball whose content was changed between two identical requests): `npx <url>` caches a remote tarball install under a hash of the URL string, in its own `_npx` cache directory, and never revalidates against the remote content on a later run with the same URL — it just re-executes whatever it installed the first time. Since the distribution URL (`.../archive/refs/heads/master.tar.gz`) is a fixed string by design (see ADR-0003), this meant a user's *first-ever* run silently pinned them to that commit forever; every subsequent double-click of `run.bat` ran that same stale copy, no matter how many times the repository was updated.

Plain `npm install <url>` does not have this problem — verified twice with the same test rig, including with `--prefix` pointed at a persistent directory reused across runs — it always fetches and extracts the URL's current content.

Fixed `run.bat` to run `npm install --prefix "%~dp0.chatdiwa-app" <tarball-url>` (reinstalling fresh on every launch, into a fixed folder next to `run.bat` so as not to pollute wherever npx's own temp cache would have put things) and then invoke `node .chatdiwa-app\node_modules\chatdiwa\bin\chatdiwa.js` directly, rather than going through `npx` at all. `node` is still run from the launcher's own working directory (unchanged from the `npx` era), so existing users' `chatdiwa.config.json` and cache folders stay exactly where they were.
